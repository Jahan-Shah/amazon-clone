Here's the tour. The feature is one end-to-end pipeline:

```
cart (localStorage) → /checkout → startCheckout action → Order(pending) + PaymentIntent
                    → Payment Element → confirmPayment → Stripe
                    → webhook marks paid → /checkout/success?order=<id>
```

### Step 1 — Stripe foundation

- `lib/stripe.ts` — a lazy singleton (`getStripe()`) mirroring `lib/db.ts`'s global-cached pattern. It's lazy on purpose: `new Stripe("")` throws at construction, so deferring it means a missing `STRIPE_SECRET_KEY` only fails when checkout is actually exercised, not at module import during `next build`.
- `.env.example` got the three Stripe vars as empty placeholders — real keys never enter the repo.

### Step 2 — `startCheckout` server action

<ref_file file="/home/jahan-shah/8x/amazon-clone/app/checkout/actions.ts" />

The security core. Control flow:

1. `getSession()` first — `userId` comes only from the server session, never the client.
2. `validateAddress` returns per-field errors (`{ success:false, fieldErrors }`), which the form renders inline.
3. Cart items arrive as `{productId, qty}` IDs only — quantities are merged into a `Map` (dedupes repeats), then every product is re-fetched from the DB. Unknown product, `qty < 1`, or `qty > stock` all reject. **The client never supplies a price.**
4. One `$transaction` writes `Address` → `Order(status:"pending")` → `OrderItem`s with `priceCents` snapshots, so order totals can't drift when catalog prices change.
5. PaymentIntent created *after* the commit with `amount = totalCents` and `metadata.orderId` — the webhook's link back. If Stripe fails, the pending order remains (honest unpaid state; a retry creates a fresh one).

Reviewer flagged F-10/F-13 here (P3): malformed payload shapes can throw instead of returning `{success:false}`, and trim/uppercase normalization is duplicated between validation and persistence.

### Step 3 — Webhook

<ref_file file="/home/jahan-shah/8x/amazon-clone/app/api/webhooks/stripe/route.ts" />

- `request.text()` for the **raw body** — `constructEvent` verifies the Stripe signature; `json()` would break verification. Missing/bad signature → 400.
- Only `payment_intent.succeeded` is handled; others get a 200-ack so Stripe doesn't retry noise.
- The cross-check `order.totalCents === intent.amount_received` means a forged-but-validly-signed event can't mark a wrong-amount order paid.
- Idempotent: only `pending` orders update; already-`paid` still returns 200. Processing errors → 500 so Stripe retries.

<ref_file file="/home/jahan-shah/8x/amazon-clone/components/checkout-form.tsx" />
